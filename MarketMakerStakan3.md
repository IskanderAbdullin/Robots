# Контекст: торговый робот MarketMakerStakan3 для OsEngine

## 1. Общая информация
- **Проект:** OsEngine (C#), путь `R:\1.OSENGINE\04.10.2026\OsEngine-master`.
- **Работаем только с файлом** `project/OsEngine/bin/Debug/Custom/Robots/MarketMakerStakan3.cs`. Роботы из `Custom\Robots` компилируются OsEngine при запуске (Roslyn), dotnet build их НЕ компилирует — проверяет только синтаксис, если файл в проекте (этот не входит).
- **ВАЖНО:** OsEngine обновляется через `Engine\Updater\Builds\Build_*` — запуск может идти из снапшота со СТАРОЙ копией Custom\Robots. После правок робота проверять, что запущен свежий экземпляр.
- Не пиши комментарии в коде вообще, фиксируй итог здесь кратко.
- В папке project изучи AGENTS, CONTEXT, CONTEXT_CODING_GUIDELINES, CONTEXT_ROBOTS_ARCHITECTURE, CONTEXT_HIGH_FREQUENCY при необходимости.

## 2. Базовые классы и API
- Наследуется от BotPanel, BotTabSimple через TabCreate(BotTabType.Simple).
- Стакан: `_tab.MarketDepthUpdateEvent`, работаем с копией `marketDepth.GetCopy()`. Bids/Asks — списки MarketDepthLevel, лучший уровень — индекс 0.
- Заявки: `_tab.BuyAtLimit / SellAtLimit` (каждая = позиция). Снятие: `_tab.CloseOrder(order)`. Перестановка: `_tab.ChangeOrderPrice` — только если `_tab.ServerIsSupportChangeOrderPrice` или `_tab.EmulatorIsOn`.
- Округление: `_tab.Security.PriceStep/VolumeStep`, цены через `_tab.RoundPrice`.
- Портфель: `_tab.Portfolio.ValueCurrent`; свободные деньги — GetPositionOnBoard() с SecurityNameCode "rub". У T-Invest список позиций может быть пуст — готовность портфеля надёжнее проверять по ValueCurrent > 0.
- Ручное сопровождение отключено: `DisableManualSupport()` + OrderTypeTime = GTC.
- Позиции журнала грузятся из `Engine\<Вкладка>DealController.txt` при старте — робот их игнорирует (чистый старт, см. п.5).

## 3. Обработка тиков
- Throttling: в IsOsTrader обработка не чаще 10 раз/сек (100 мс). В тестере без ограничения. В IsOsOptimizer — сразу выход. Режим Off не троттлится.
- Вся работа под `_planLock`; OrderUpdateHandler чистит словари под тем же lock.

## 4. Параметры робота
- Режим (Off/On); режим покупки («Один уровень (макс. объём)» / «Распределение сверху вниз» / «Перед большой заявкой» / «Перед заявкой заданного объёма»); суммарный объём покупки; объём чужой заявки в лотах (умолч. 1000); % от объёма уровня; режим объёма продажи («% от бумаг в портфеле» / «% от всего портфеля»); % продажи; режим объёма покупки («Фиксированный» / «% от стоимости портфеля» / «Максимум без маржи»); мин. объём стены (умолч. 100000); превышение над медианой (умолч. 3); проверка моргания N тиков (умолч. 3) — анти-спуфинг стены И окно сглаживания бюджета продажи.

## 5. Действующая логика

### Покупка
- «Один уровень»: одна заявка на бид-уровне с макс. чужим объёмом (GetForeignVolumes).
- «Перед большой заявкой»: одна заявка на 1 PriceStep выше первой стены (чужой объём >= мин. стены И >= множитель × медиана). Анти-спуфинг: стена должна подтвердиться N тиков подряд на одной цене. Цена стены + PriceStep >= лучший аск — не ставим.
- «Перед заявкой заданного объёма»: одна заявка на 1 PriceStep выше первой от лучшего бида заявки с чужим объёмом >= заданного. Собственный объём рассчитывается по общим настройкам покупки. Цена >= лучший аск — не ставим. Поле объёма чужой заявки используется только в этом режиме.
- «Распределение сверху вниз»: от лучшего бида вниз, объём = min(%/100 × чужой объём уровня, остаток), округление вниз до VolumeStep, 0 — пропуск.

### Продажа
- Всегда распределением от лучшего аска вверх по той же формуле.
- Бюджет плана (GetSellPlanVolume, режим «% от бумаг») = свободные бумаги + остатки наших Sell-заявок × %/100 — план не зависит от блокировки бумаг своими заявками.
- **НЕ УБИРАТЬ:** свободные бумаги = PositionOnBoard.ValueCurrent − ValueBlocked (двойной счёт ValueBlocked в T-Invest, баг 0.3).
- Бюджет плана ограничен `_sellPapersBase` = минимум GetSellPlanVolume за последние N тиков (`rest = _sellPapersBase`) — гасит ложный рост бюджета при лаге ValueBlocked у брокера. Рост бюджета входит в план только продержавшись N тиков.
- Гистерезис по чужому объёму: `_sellForeignBasis` (цена → мин. чужой объём с последней смены базы) — рост чужого объёма план не увеличивает.

### Окно успокоения (баг 12)
- После любых своих действий с заявками (place/cancel/changePrice) штампуется `_lastOwnOrdersChange`; в течение OwnOrdersSettleTime = **0,4 сек** ApplyStandingOrdersFloor подпирает план на ценах стоящих заявок их остатком (только поднимает объём на совпадающих ценах, новые цены не добавляет). Гасит гонку: позиции/портфель обновляются раньше, чем стакан показывает наши заявки → GetForeignVolumes дважды вычитает нас → ложное съёживание плана → cancel/place, заблокированный клэмпом.

### Чистый старт
- Позиции, восстановленные журналом на момент создания робота, игнорируются логикой (`_restoredPositionNumbers`, фильтр в GetMyActiveOrders) — робот не усыновляет старые заявки и не снимает их в Off. Внимание: реально висящие на бирже заявки прошлой сессии продолжают блокировать бумаги/деньги.

### Таймер старта
- Первый тик On: лог «Робот включён в режим "On"», штамп `_onTime`. Один раз при готовности портфеля: «Портфель получен через X сек после включения». Готовность = Portfolio != null и (ValueCurrent > 0 или непустые позиции).

## 6. Сверка плана с заявками
- План строится каждый обработанный тик; активные заявки — из _tab.PositionsAll → OpenOrders (Active/Partial, плюс Pending/None у Opening), один раз за тик.
- Быстрый выход: OrdersMatchPlan (мультимножество + допуск VolumesMatch).
- **VolumesMatch:** Sell — рост плана = несовпадение сразу, снижение — совпадение пока план ≥ стоящий − max(VolumeStep, 10% стоящего). Buy — совпадение пока стоящий ≥ план − max(VolumeStep, 20% плана).
- Перестановка одной заявки через ChangeOrderPrice (очередь сохраняется); повторный запрос на ту же цену — не чаще 60 сек (_ordersOnPriceChange).
- ApplyPlanSide: префикс 0..k−1 не трогаем; с k-й — снимаем всё и проставляем план (замена занимает два тика). Бюджетный клэмп: reserved = остатки всех активных заявок стороны (включая снимаемые), canPlace = бюджет − reserved.
- Повторный отзыв той же заявки — не чаще 60 сек (_ordersOnCancel).

## 7. Особенности ядра (не правим, работаем только с роботом)
- «Сделка не открылась ... OpeningFail» — штатный лог ядра (BotTabSimple.cs:7926): отзыв неисполненной открывающей заявки = OpeningFail позиции, по сообщению на позицию. Возникает и при снятии заявок в Off.
- Портфель от сервера приходит быстро (замерено 0,0 сек от On); основная пауза до первых заявок — сам запуск робота OsEngine после нажатия On (~5-8 сек), вне компетенции робота.

## 9. Возможные причины нестабильности и скачков заявок

Ниже — гипотезы, а не подтверждённый диагноз. Точную причину можно установить только по журналам и воспроизведённой последовательности событий.

### 9.1. Гонка стакана, портфеля и собственных заявок

Наиболее вероятный сценарий: после выставления заявки портфель уже заблокировал объём, а стакан ещё не отражает заявку или отражает её с задержкой. На следующем тике GetForeignVolumes может повторно вычесть собственный объём, план ложно уменьшается, заявка отменяется. После отмены баланс и стакан обновляются, план снова растёт, заявка выставляется на другом уровне.

Признаки: скачки возникают сразу после собственных place/cancel/changePrice; перед ними меняются свободный баланс, чужой объём или план без сопоставимого внешнего изменения рынка.

Окно OwnOrdersSettleTime = 0,4 сек смягчает симптом, но не доказывает устранение причины.

### 9.2. Смешение свободного и заблокированного объёма

ValueCurrent − ValueBlocked отражает свободный остаток, но не весь контролируемый роботом объём. При активных заявках нулевой свободный баланс может быть нормальным состоянием.

Нельзя независимо складывать свободный баланс и остатки заявок по данным разных моментов: возможен двойной учёт. Нужна единая модель: свободный баланс, остаток каждой собственной заявки, исполненный объём и подтверждённые терминальные статусы.

### 9.3. Повторная реакция на собственные действия

Собственная заявка меняет стакан, после чего следующий пересчёт может воспринять это как новый внешний сигнал. Если чужой объём, база плана и активные заявки рассчитываются по несогласованным снимкам, возникает цикл cancel/place.

Проверить: появляется ли новое действие при неизменных внешних данных; учитываются ли собственные заявки одинаково во всех функциях; нет ли разных правил их исключения в GetForeignVolumes и OrdersMatchPlan.

### 9.4. Сравнение сырой и округлённой цены

Если целевая цена до RoundPrice сравнивается с фактической ценой заявки после округления, одна и та же биржевая цена может считаться разной на каждом тике.

Проверить: каноническая цена должна вычисляться один раз, а сравнение вестись с Order.Price после применения того же правила округления. Нужны проверки значений PriceStep, Decimals и преобразований double → decimal.

### 9.5. Неподтверждённые операции и повторные команды

CloseOrder и ChangeOrderPrice являются запросами, а не гарантией результата. Повторная команда до подтверждения предыдущей может создать очередь противоречивых операций. ChangeOrderPrice допустим только при подтверждённой поддержке сервером; для TInvest нельзя предполагать такую поддержку.

Проверить: нет ли повторных place/cancel/changePrice для того же NumberUser до терминального события; как обрабатываются Fail, Partial, Cancel после Partial и таймаут ответа.

### 9.6. Потоковые и повторные события

MarketDepthUpdateEvent, события заявок, сделок и портфеля могут приходить из разных потоков и в разном порядке. Сделки могут дублироваться из потока и polling. Один _planLock не помогает, если часть состояния читается или изменяется вне его.

Проверить: все ли поля плана и заявок защищены одной синхронизацией; дедуплицируются ли сделки по NumberTrade; монотонно ли учитывается VolumeExecute; нет ли реентерабельного вызова обработчика во время торгового метода.

### 9.7. Штатные изменения стратегии, похожие на сбой

Продажа распределяется по нескольким уровням, а стены, медиана и чужие объёмы могут меняться каждый тик. Поэтому не каждое перемещение заявки является ошибкой. Нужно отделить изменение плана из-за внешнего рынка от изменения, вызванного только собственной заявкой.

### 9.8. Ошибки журнала и версия исполняемого кода

OpeningFail после отмены неисполненной открывающей заявки может быть штатным сообщением ядра, а не биржевой ошибкой. Также нужно исключить запуск старой копии робота из снапшота Updater: иначе исправления могут не попадать в фактически исполняемый код.

## 10. План диагностики и исправления

### Этап 1. Зафиксировать фактическое поведение без изменения логики

Добавить временный диагностический журнал вокруг проблемы. Для каждого торгового действия записывать:

- время с миллисекундами и последовательный номер события;
- причину действия и тип исходного события;
- лучший Bid/Ask, целевые цены и округлённые цены;
- ValueCurrent, ValueBlocked, свободный баланс и остатки собственных заявок;
- чужой объём, базу плана и итоговый план по сторонам;
- NumberUser/NumberMarket, статус, VolumeExecute и остаток заявки;
- результат вызова place/cancel/changePrice и последующее подтверждение.

Не вести такой подробный журнал постоянно: включать его только для ограниченного диагностического прогона. Сопоставить несколько скачков с конкретными последовательностями событий и классифицировать сообщения OpeningFail отдельно от реальных отказов.

### Этап 2. Сделать воспроизводимые локальные проверки

На поддельных событиях проверить как минимум:

1. Портфель заблокировал объём раньше, чем стакан показал собственную заявку.
2. Стакан обновился раньше портфеля.
3. Повторный стакан без внешних изменений не меняет план.
4. Округлённая цель совпадает с Order.Price и не вызывает перестановку.
5. Partial → Cancel пересчитывает только фактический остаток.
6. Cancel → Done в гонке не создаёт новую заявку.
7. Повторный MyTrade с тем же NumberTrade не учитывается дважды.
8. Повторный MarketDepthUpdateEvent не создаёт параллельных команд.
9. Таймаут отмены переводит робота в безопасное состояние без blindly-повтора.
10. Off во время активной операции запрещает новые заявки и корректно завершает отмену.
11. Рестарт со старыми заявками не присваивает их и не запускает новый план поверх неизвестного состояния.
12. Пустой, частичный или невалидный стакан не создаёт заявку с нулевой ценой.

Сначала воспроизвести сбой на записанной последовательности, затем исправлять. Тест должен падать до исправления и проходить после него.

### Этап 3. Приоритетные изменения архитектуры

1. Ввести единый автомат исполнения: нет операции → выставление/изменение → ожидание подтверждения → сверка. Параллельные торговые команды запретить.
2. Отделить чистый расчёт плана от обращений к BotTabSimple. Планировщик получает один согласованный входной снимок и возвращает план без побочных действий.
3. Вести реестр собственных заявок по NumberUser; NumberMarket добавлять при появлении, не используя его as единственный ранний идентификатор.
4. Получать снимок стакана через GetCopy и один раз за обработку формировать входные данные плана. Не читать изменяемые коллекции в разных частях расчёта повторно.
5. Сравнивать фактические заявки с планом по каноническим ценам и объёмам. При неизменном плане не выполнять торговых действий.
6. Разделить свободный баланс, зарезервированный собственными заявками объём и исполненный объём. Не принимать решение по одному лаговому событию портфеля.
7. Перед каждой отменой или перестановкой записывать причину. Запретить повторную команду тому же ордеру до подтверждения предыдущей.
8. При неизвестном состоянии, таймауте или расхождении событий переходить в Error и требовать сверку, а не продолжать автоматические выставления.
9. Сохранить DisableManualSupport и чистый старт, но явно контролировать оставшиеся на бирже старые заявки и их блокировки.

Не менять одновременно стратегию, допуски VolumesMatch, окно успокоения и исполнительный автомат: иначе будет непонятно, какое изменение устранило проблему.

### Этап 4. Корректировать защитные механизмы по доказательствам

- OwnOrdersSettleTime оставить как временную защиту, если её эффект подтверждён журналами; не считать её заменой корректной синхронизации.
- Throttling применять для ограничения частоты пересчётов, сохраняя последнее целевое состояние. Не отбрасывать события без сохранения актуальной цели.
- Повторные запросы на ту же цену и повторные отмены ограничивать прежде всего состоянием операции, а не только интервалом 60 секунд.
- Допуски VolumesMatch и сглаживание бюджета менять только после проверки граничных случаев: слишком широкий допуск может скрывать реальное расхождение плана и заявок.

### Этап 5. Проверка и постепенный запуск

1. Локальные детерминированные проверки и воспроизведение записанных сбоев.
2. Проверка, что запущенная копия робота соответствует изменённому файлу, а не старому снапшоту.
3. Read-only подключение: стакан, портфель и собственные заявки без отправки новых, только с разрешения пользователя.
4. Любые реальные ордера — отдельно, с явным разрешением, минимальным объёмом и ручным контролем.
5. Измерять задержки события → решения → подтверждения и долю самопроизвольных cancel/place. Сравнивать поведение до и после каждого отдельного исправления.

Переход на прямой TInvest API рассматривать только после того, как планировщик и автомат состояния проверены. Сам по себе переход не устранит гонки и двойной учёт, но может дать больше контроля над UID, событиями и восстановлением, если ограничения адаптера останутся подтверждённой причиной проблем.

## 11. Критерии устранения проблемы

- При неизменных внешних данных повторные события не меняют план и не создают торговых действий.
- Собственные заявки не вычитаются из чужого объёма дважды.
- Одна и та же каноническая цена не вызывает цикл перестановки.
- Нет параллельных или повторных команд к одной заявке до подтверждения предыдущей операции.
- Частичное исполнение и отмена не приводят к превышению доступного баланса или двойному учёту.
- Каждое изменение заявки объясняется записанной причиной и идентификаторами входных данных.
- Неизвестное состояние приводит к безопасной остановке, а не к blindly-новым заявкам.
- Воспроизведённые ранее сбойные последовательности проходят локальные проверки.
