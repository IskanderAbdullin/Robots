# Стенд MarketMakerStakan3

Стенд проверяет актуальный `MarketMakerStakan3.cs` без брокера и без создания настоящего торгового таба. Использован подход стендов PortfolioSeller и BestAskBestBidOnly: исходник робота включается непосредственно в тестовую сборку, события доставляет поддельный API, а установленные типы OsEngine проверяются отдельно.

Установка рядом с роботом:

```text
OsEngine/bin/Debug/
  Custom/Robots/MarketMakerStakan3.cs
  Custom/RobotTestStands/MarketMakerStakan3/
    run.ps1
    MarketMakerStakan3.TestStand.csproj
    Fakes.cs, Harness.cs, Program.cs, Modules/
    RealApi/
    Baseline/MarketMakerStakan3.cs.txt
    reports/
```

Стенд находится вне `Custom/Robots`, потому что OsEngine рекурсивно ищет там исходники `.cs`. Тестовые классы и fake API не должны попадать в список торговых роботов. Только основной исправленный файл предназначен для `Custom/Robots`.

## Запуск

Нужен .NET 10 SDK. Внешних NuGet-пакетов и реального подключения нет. Запускать из папки стенда:

```powershell
.\run.ps1
.\run.ps1 -Module planning,budgets -SkipRealApi
.\run.ps1 -Module property -Seed 4217 -Iterations 1000 -SkipRealApi
.\run.ps1 -Baseline -SkipRealApi
```

Если выполнение скриптов запрещено настройкой PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\run.ps1
```

`-RobotSource` задаёт другой исходник, `-EngineBin` — папку с нужной `OsEngine.dll`. Без параметров установленные пути вычисляются относительно стенда. Локальная рабочая копия также поддерживается. `-SkipRealApi` позволяет запускать поддельный стенд без установленного движка. `-Baseline` компилирует сохранённый исходник до этих исправлений: провалы регрессионных сценариев там ожидаемы, код возврата остаётся ненулевым.

Прямой запуск и список сценариев:

```powershell
dotnet run --project .\MarketMakerStakan3.TestStand.csproj -- --list
dotnet run --project .\MarketMakerStakan3.TestStand.csproj -- --module execution --seed 4217 --iterations 1000
dotnet run --project .\RealApi\RealApi.csproj
```

CLI: `--module all|name,other-name`, `--seed N`, `--iterations N`, `--source path`, `--json path`, `--list`, `--quiet`, `--help`. Фильтр выбирает модуль либо подстроку названия сценария. Коды возврата: 0 — все выбранные проверки прошли; 1 — провал сценария; 2 — неверные аргументы или несовпадение исходника. Для подмены исходника передавать MSBuild `-p:RobotSource=...`, а не только `--source`. Скрипт делает это сам. SHA256 исходника фиксируется при компиляции и проверяется перед прогоном.

`run.ps1` сохраняет текстовый журнал и JSON с результатами в `Logs/`. JSON содержит SHA256 исходника, seed, параметры, результаты по модулям, ошибки и последовательность событий проваленного сценария. Проверяйте код возврата вместе с отчётом: один успешный модуль не означает успех всего стенда.

## Что проверяется

- Жизненный цикл: On/Off, ожидание подтверждения, отмена нескольких заявок по очереди, таймаут, постоянный Error, удаление и отписка, восстановленный журнал.
- Исполнение: одна неподтверждённая операция на обе стороны; Active/Partial/Cancel/Done/Fail; неоднозначный ответ и исключение отправки; подтверждение перестановки точной ценой; неизвестные и повторные отчёты.
- План: четыре режима покупки, медиана и подтверждение стены, пороги, собственный остаток, распределение от лучшей цены, гистерезис и сглаживание продажи.
- Бюджеты: свободный и зарезервированный объём, частичное исполнение, лотность, отрицательные/неоднозначные остатки, фиксированный, процентный и денежный режимы отдельно.
- Входные данные: пустой, частичный, неупорядоченный, перекрещённый и нечисловой стакан; округление, шаг цены и объёма; готовность соединения.
- События: синхронный callback внутри торгового метода, вложенный стакан, несколько потоков, задержка сырого отчёта относительно журнала и обновления портфеля.
- Диагностика: журнал по умолчанию выключен, идентификаторы и причина команды, ограничение окна, повторное включение и ограничение сообщений об ошибке.
- Прогоны с фиксированным seed: события автомата и независимый учёт потенциально исполнимых остатков. Отмена до терминального подтверждения не освобождает резерв в модели брокера.

Фиксированный и процентный режимы покупки сохраняют исходные допущения о марже. Проверка «не тратить больше свободных денег» относится к режиму «Максимум без маржи». Проверка продажи физических бумаг относится к «% от бумаг в портфеле»; режим «% от всего портфеля» не превращён в другую стратегию.

## Проверка установленной DLL

`RealApi` компилирует исправленный робот с DLL выбранного движка и выполняет 12 отдельных проверок `MarketDepth`, `Order`, `Position` и дедупликации `MyTrade`. Настоящий `BotPanel` не создаётся, подключений и заявок нет. Отчёт содержит путь и SHA256 загруженной DLL.

Одна проверка специально характеризует особенность журнала: `Position.SetOrder` после сырого `Cancel` с `VolumeExecute=3` может оставить в журнале исполнение 0 до `MyTrade`. Это проверка предпосылки модели, а не доказательство безопасной торговли. Изменение поведения DLL требует пересмотра соответствующего сценария, поэтому такое расхождение не скрывается.

## Границы проверки

Fake API не заменяет сервер и полный журнал OsEngine. Он не воспроизводит сетевой протокол, хранение журнала на диске, произвольные действия других роботов, все состояния подключения или все возможные чередования потоков. Тестовый таймер выключен, его callback вызывается вручную; сроки сдвигаются через reflection. Это проверяет решения по времени, но не точность реального планировщика Windows. Многопоточные сценарии проверяют выбранные гонки, а не полный перебор.

Событие портфеля после операции не доказывает актуальность каждого числового остатка. Неверные или постоянно устаревшие данные брокера остаются ограничением. Полного нефильтрованного снимка старых обычных и стоп-заявок через брокерский API этот стенд не добавляет. Неизвестные заявки вне журнала могут оставаться незамеченными. Денежный режим ориентирован на RUB; универсального выбора валюты и модели обеспечения деривативов здесь нет. Стоимость лота исправляется для `SecurityType.Stock`; для других типов остаются допущения существующей стратегии.

Новый `MarketMakerStakan3_InventoryDrivenPlan.md` использован как источник вопросов для проверки. Полный новый процесс запуска и архитектура из него не реализованы в рамках создания стенда. Старая проблема включения собственной заявки в стакан по-прежнему требует воспроизведения на записанных брокерских событиях; окно 0,4 секунды остаётся эвристикой.

Исходные коды ядра и коннектора не изменяются. Стенд не запускает OsEngine, MCP-стенд или реальные заявки. Результаты конкретного проверенного прогона и найденные исправления приведены в `REPORT.md` и `reports/`.
